# Architecture Decision Records

## 철학
MVP 프로토타입 속도 최우선. 아직 배포된 적 없는 앱이므로, 실제로 부딪힐 가능성이 낮거나 아직 존재하지 않는 문제(구버전 데이터, 멀티탭 동기화, 용량 초과 등)에 대한 선제 대응은 하지 않는다. 코드 몇 줄로 처리 가능하고 실제로 자주 마주칠 문제(빈 값 검증, 실수로 인한 캐스케이드 삭제, 손상된 데이터로 인한 크래시)만 방어한다.

---

### ADR-001: Next.js (App Router) 유지
**결정**: 데이터가 전부 브라우저 localStorage에만 저장되는 클라이언트 전용 MVP임에도 Next.js App Router를 프레임워크로 유지한다.
**이유**: 로그인/서버 저장을 추후 추가하기로 이미 확정되어 있어, 그 시점에 API 라우트를 마이그레이션 없이 같은 프로젝트에 바로 추가할 수 있다.
**트레이드오프**: 지금 당장은 SSR/RSC 이점을 전혀 쓰지 못하면서 `"use client"` 경계 관리 등 Vite+React SPA보다 약간의 프레임워크 복잡도를 더 가져간다. (리서치 결과 "지금은 클라이언트 전용, 나중에 백엔드" 시나리오엔 Vite로 시작하는 게 더 흔한 권장이지만, 마이그레이션 단계를 없애는 이점을 우선했다.)

### ADR-002: Zustand + persist 미들웨어로 로컬 저장
**결정**: 직접 만든 `storage.ts` + `repositories` 계층 대신 Zustand의 `persist` 미들웨어로 단일 스토어(`useAppStore`)를 구성해 localStorage 동기화를 처리한다.
**이유**: 화면마다 훅이 상태를 독립적으로 들고 있으면 한 화면에서의 변경이 다른 화면에 자동 반영되지 않는 문제가 설계 검토 중 발견됐다. Zustand는 구독/동기화를 라이브러리 차원에서 해결해줘 직접 짜야 했던 코드가 크게 줄어든다.
**트레이드오프**: 외부 의존성이 하나 늘고, Next.js SSR과 결합할 때 하이드레이션 타이밍을 신경 써야 한다(`skipHydration` + 수동 `rehydrate()` 필요).

### ADR-003: 신규 상품은 이름+첫 가격을 한 화면에서 동시 입력
**결정**: 가격 메모 탭에서 상품을 처음 등록할 때 상품명과 첫 가격을 하나의 폼에서 함께 입력받아 `Product`와 첫 `PriceEntry`를 원자적으로 생성한다.
**이유**: "상품 등록 → 그 상품을 다시 선택해 가격 입력"의 2단계 흐름은 매장에서 실제로 쓰기엔 번거롭다는 점을 사용자 흐름 검토에서 확인했다.
**트레이드오프**: 신규 등록 폼(`ProductAddModal`)과 이름만 바꾸는 수정 폼(`ProductRenameModal`)을 별도 컴포넌트로 나눠야 해 컴포넌트 수가 하나 늘어난다.

### ADR-004: 테스트 스택은 Vitest + Testing Library
**결정**: Vitest + @testing-library/react + jsdom을 테스트 프레임워크로 채택한다.
**이유**: Next.js 공식 App Router 테스트 가이드가 권장하는 조합이며, 클라이언트 컴포넌트와 localStorage 기반 로직(jsdom이 `localStorage`를 지원) 테스트에 문제가 없음을 확인했다. 저장소의 tdd-guard 훅이 구현 파일마다 테스트를 강제하므로 실행 속도가 중요하다.
**트레이드오프**: 비동기 서버 컴포넌트는 Vitest로 테스트할 수 없다(공식적으로 Playwright/E2E 권장) — 이 프로젝트는 전부 클라이언트 컴포넌트라 해당 사항 없음. `next/navigation`의 `useRouter`/`usePathname`은 jsdom에서 기본 동작하지 않아 라우팅 관련 테스트에서 별도 mock이 필요하다.

### ADR-005: 에러 처리 범위를 MVP 수준으로 최소화
**결정**: 이름/가격 검증, 손상된 JSON 파싱 실패 시 조용한 초기화, 최상위 Error Boundary, 캐스케이드 삭제 확인 다이얼로그, 폼 이중 제출 방지만 구현한다. localStorage 용량 초과 전용 처리, 프라이빗 브라우징 감지+폴백 모드, 구버전 스키마 자동 마이그레이션은 만들지 않는다.
**이유**: 데이터 용량이 작아 용량 초과는 현실적으로 발생하지 않고, 프라이빗 모드 문제는 발생해도 크래시가 아닌 자연스러운 열화(새로고침 시 데이터 미저장)에 그치며, 아직 한 번도 배포된 적 없는 프로토타입이라 "구버전 데이터" 자체가 존재하지 않는다.
**트레이드오프**: 위 세 가지 시나리오가 실제로 발생하면 사용자에게 안내 없이 조용히 실패하거나(용량 초과), 앱이 정상 동작하지만 데이터가 저장되지 않는다(프라이빗 모드). 필요해지면 그때 추가한다.
